# 长时运行 Agent 停止条件

当项目使用 `/loop`、自主 agent 或任何长时运行 agent 流时，由 `health` 步骤 1c 加载。没有此类流的项目完全跳过。

项目必须定义明确的停止条件。一个永不停止的 agent 就是一场迟早发生的预算与安全事件。

审计以下四个硬性停止信号；把每一个的缺失都标记为一条 Structural 发现：

1. **连续两个检查点之间没有进展。** 相同的文件被改动、相同的错误被记录、没有新的提交/测试/输出。建议杀掉循环并暴露状态，而不是重试。
2. **重复的相同失败。** 相同的堆栈跟踪、相同的错误信息、相同的失败断言连续出现三次，说明假设是错的；更多尝试不会有帮助。
3. **成本或 token 预算超限。** 项目应声明每次运行的预算（token、API 花费、挂钟分钟数）。循环应在预算触及时退出，而不是在工作完成时退出。
4. **外部阻塞。** 目标分支上的合并冲突、agent 无法解决的依赖锁、缺失的凭据、网络不可达。其中任何一项都应中止循环并询问用户，而不是永远重试。

停止条件应位于被跟踪的项目文档中（`AGENTS.md`、循环的启动脚本或专门的配置），而不只是 agent 的 prompt 里。Prompt 会被遗忘；被跟踪的配置可强制执行。当项目支持时，优先推荐 hooks（对相关工具的 PostToolUse）而非 prompt 指令：hook 物理上无法被跳过，prompt 指令可以。在推荐某个 hook 之前，先确认宿主机的 hook 覆盖范围：某些 agent 只对一部分工具触发 PostToolUse（例如某运行时可能只匹配 shell/Bash），因此必须在文件编辑后运行的修复应改挂在 Stop 或会话结束 hook 上。
