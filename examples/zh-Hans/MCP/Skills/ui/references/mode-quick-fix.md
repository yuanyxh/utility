# 视觉快速修复模式

当诉求是对既有界面做有边界的视觉修正、而非新建时，从 `ui` 加载本文。

当用户带着一个具体症状要求做一次窄范围的视觉修复时激活：溢出、被裁切或折行的文本、错位、间距失衡、对比度/可读性、本地化文本放不下，或紧凑状态下的响应式断裂。这是修一个既有界面，不是重设计它。

流程：

1. 读取当前 UI 证据：截图、渲染出的页面、原生视图，或对应组件。
2. 用一句话指出确切的视觉缺陷。
3. 做出修复该缺陷的最小材质、几何、间距、对比度、排版或文本适配改动。
4. 验证真实运行中的界面或生成的产物。检查长单词、本地化字符串、紧凑状态，并在适用时至少检查一个窄视口。终端输出也算渲染界面：改动面向 CLI 的文本或布局后，重新运行命令并阅读实际输出，检查整个输出（而不只是改动的那一行）的列对齐、块间距与图标一致性。
5. 如果修复牵涉三个或更多组件、改变产品行为，或暴露出方向问题，停下并切换到 `references/mode-screenshot-iteration.md` 或 `SKILL.md` 的「先锁定方向」小节。

**间距统一规则。** 一个间距或尺寸值调了三次仍显得不对，那就是结构问题，不是数值问题：把 N 个独立取值收敛成一个共享的命名 token（`Spacing.s4`、`--gap-content`），外层容器内边距默认等于内层元素间距。关于「间距即系统」的细节见 `references/design-reference.md`。

**固定高度的动作槽位，统一的排版。** 任何会依据状态替换子项的容器（状态栏、动作槽位、工具栏行、菜单项）都必须在所有状态间使用同一字号。变化的是填充、描边、不透明度、颜色或图标，绝不是字号。`secondary 13px` 与 `primary 14px` 之间 1pt 的高度差，会在状态切换时变成可见的抖动。同一槽位内的 CTA 胶囊按钮使用相同尺寸（通常 14px），靠背景与边框区分，而不是靠排版。

**加载中不等于空。** 仍在加载、测量、索引、刷新，或等待权限的界面必须渲染一个 pending 状态，而不是最终的空白文案。只有当请求以空结果完成之后，才显示「什么都没找到」。如果刷新期间既有结果可见，让它们保持可见地陈旧，或用进度替换它们；绝不要在工作仍在进行时闪现一个最终的空状态。

**安全边界内的操作设计。** 对清理、删除、卸载、重置或改变权限的界面，不要通过隐藏可恢复性来让 UI 显得更简单。批量选择、自动选择、一键删除，或「推荐」的破坏性默认值，只有在每一行对目标用户可理解、且携带足够身份信息以核验安全时（名称、来源、所有者、路径、预览，或相关的恢复含义）才适用。如果各行是不透明标识、被推断出的残留项，或只有机器能读懂的路径，优先选「先审阅」式 UI、限定当前目标范围、禁用破坏性可供性，或用解释性分组，而不是更快的批量控件。一个「少点几下」的功能请求，不足以取消用户核验将要改变什么的能力。

**安静的产品边界。** 更少的点击与更丰富的控件并不自动更好。在增加替代控件之前先移除误导性可供性，对诊断与告警偏好安静的默认值，并在改变速度或新增动效偏好之前先修复不稳定的动效节奏。如果当前 UI 暗示了一个它无法支撑的动作、状态或承诺，先移除那一暗示。完成态界面遵循同样的立场：以用户此行的单一结果打头，把解释放在摘要行之后的详情浮层里，并隐藏任何背后空无一物的可供性（一条空的「跳过 0 项」条目，一个与「点这一行本就做的事」重复的按钮）。
