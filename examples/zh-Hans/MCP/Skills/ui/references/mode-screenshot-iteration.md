# 截图迭代模式

当用户提供一张已渲染界面的截图、希望依据该证据改进时，从 `ui` 加载本文。

当用户发来截图或图片并附带一句吐槽（「这里很丑」「这个不对」「fix this」「looks wrong」）时激活。既有产品就是方向。跳过五问式的方向锁定。

**流程：**

1. 读截图。用一句话陈述问题：具体是什么看起来不对（间距、对比度、对齐、字体、颜色、密度、层级）。当用户的负面标签具有诊断价值时予以保留；不要把「丑」「乱」「不清晰」或「怪」翻译成含糊的「让它现代一点」式说法。
2. 在碰代码之前，等用户确认诊断。
3. 如果用户提供了参考截图、旧版本，或「这张是好的」示例，先对照当前与参考，在选定修法之前点明视觉差异。
4. 如果诊断是已知的 UX 问题（分栏同步、无限滚动、虚拟列表、吸顶头部），花一轮调研同类别中 2-3 个成熟产品如何解决它，然后再写代码。引用各自的做法。仅当修复纯粹是外观层面的（颜色、间距、文案）时才跳过。
5. 找到对应的代码：grep 组件名或类名，读实际文件。不要依赖记忆或对文件位置的假设。
6. 施加最小修复。对既有产品，先尝试材质/不透明度、几何、间距、排版或文本适配调整，再考虑重设计界面。
7. 在浏览器、原生 App、截图工具或渲染产物中验证结果，适用时在桌面宽度与 375px 移动宽度下都验证。检查长单词、本地化字符串、按钮标签与紧凑状态的溢出。如果宿主无法渲染，明确说明，并把用户应当检查的那一确切视图交接出去。
8. 请用户在浏览器中验证。没有这一步就不要交接。

**校准规则：**
- 用户的截图是本轮最强的设计简报。在修复完成之前，让它一直留在推理视野里。
- 真实运行中的产品是权威。产品页面、App 截图、发布页与当前 UI 状态凌驾于泛泛的风格直觉之上。
- 不要把具体的品味反馈压平成一堆泛泛的 UI 形容词。「更高级」不是一条诊断；「标题基线漂到了中文行的上方」才是。
- 如果截图暴露的是回归、渲染损坏、时序问题或生成素材缺陷，而非品味问题，转到 `/hunt` 并保留视觉证据。

**原生截图交接。** 对原生 App，一旦你已证明 App 能构建、能运行、能到达目标视图，就不要为了截取最终视觉凭证而反复与焦点、窗口层级或坐标点击自动化缠斗。做一次有边界的自动化尝试。如果它不稳定，点名确切的界面，并请用户提供截图来迭代。这是视觉 QA 的边界，不是构建/运行验证的替代品。

**边界**：如果修复需要改动 3 个或更多组件，或者它暴露的是方向问题而非某个具体 bug，就暂停，并在继续之前跑完整套方向锁定。

**重设计优先级顺序**（在改造既有 UI 而非从头构建时）：更换字体 → 清理颜色 → hover/active 状态 → 布局与留白 → 替换通用组件 → 增加加载/空/错误状态 → 排版精修。这个顺序能最大化视觉提升，同时最小化每一遍的波及范围。完整规则、常见陷阱与绝对 CSS 禁令都在 `references/design-reference.md`。
