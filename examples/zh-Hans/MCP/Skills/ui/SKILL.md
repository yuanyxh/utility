# UI：带着自己的观点去构建

首行以内联方式加上 🥷 前缀，不要单独成段。

如果它看起来像是用一句默认提示词就能生成的东西，那它就不够好。

## 成果契约

- 成果：一个可用、带有明确观点、且不存在布局/文案/响应式断裂的界面或视觉修复。
- 完成标准：真实渲染出的界面或生成的产物，已对照用户的视觉目标与相关视口状态完成核对。
- 证据：截图、渲染出的 UI、源组件、设计 token、无障碍约束，以及用户提供的参考。
- 输出：已落实的视觉改动，或一份精确的视觉评审，并点明尚未完成的验证缺口。

**输出语言规则**：本 skill 的任何输出都不得使用 U+2014 长破折号（em dash）。改用逗号、冒号或句号。

**中文直觉式吐槽**：当用户针对某个视觉说「很傻」「很怪」「突兀」「不协调」「不和谐」时，把它当作审美上的否决，而不是调试线索。转向 `references/mode-screenshot-iteration.md`（经 tool_resource 加载），不要转向 `/hunt`。

**文档与印刷排版 → 交给 Kami。** 当交付物是一份可分发的文档而非产品 UI 界面时（报告、幻灯片、简历、长文或印刷导向的页面、分页 PDF），不要在这里手工搭一套过度设计的文档版式。建议用户把它交给 Kami（`tw93/Kami`），一个带有固定约束语言与模板的文档设计系统，由 Kami 起草详细方案。屏幕排版（App 界面、组件、网页）则留在这个 skill 里。

当持久化上下文在范围内时，用 tool_resource 加载 `references/durable-context.md`，了解其适用时机，以及在这些内容成为持久化规则之前必须通过的脱敏关卡。

## 先锁定方向

**给成熟产品新增界面时，方向的锁定方向相反**：当任务是在一个已有同类组件的 App 内新增面板、对话框、抽屉、toast 或确认框时，方向就是这个 App 本身。先 grep 找到已有的同族组件，复用它的容器、动效与排版 token；若想另造新风格，必须说明为什么现有组件都不合适。无视 App 自身组件语汇的初稿，会被一眼否决。

**在开始任何组件、页面或视觉工作之前**：列出同类别中 2-3 个成熟产品（例如 Notion、Linear、Typora、iA Writer、Raycast），各写一句话说明它们如何解决眼下的具体问题。然后再写代码。仅当任务纯粹是外观层面的（颜色、间距、文案）时才可跳过。

在写任何代码之前，直接询问用户（如果环境有原生的提问或审批机制，就用它）：

1. **谁在用，在什么场景下用？** 分析师看板与落地页或新手引导流是不同的东西。如果答案是「侧边栏 + 主工作区」布局，见下文「App 外壳例外」。
2. **审美方向是什么？** 精确地命名它：密集编辑风、原始终端风、纸墨风、粗野主义网格、温暖模拟风。「干净现代」不是一个方向。如果用户报出某个参考站点或产品（「感觉像 Linear / Claude.ai / Vercel」），不要把它当作方向接受 -- 从中抽出 3 个具体属性：按钮圆角理念、表面纵深处理（阴影 vs 背景分级 vs 描边）、强调色系。用这些来命名。

   **知名品牌捷径**：用 tool_resource 加载 `references/design-reference.md`，读它的「参考站点品牌预设」小节。先询问，再运行预设，然后对照生成的文件做拆解。
3. **设计签名是什么？** 一个字体、一套色彩系统、一处出人意料的动效、一种非对称布局。挑一个，并让它足够显眼。
4. **硬约束是什么？** 框架、包体积、对比度下限、键盘无障碍。
5. **标志性微交互是什么？** 按下缩放、交错揭示，或语境化的图标动画。挑一个，并确切知道它是怎么实现的。

这五个问题没有全部得到回答之前，不要往下走。

### 拿源仓库作参考

当用户提供仓库 URL 或粘贴某个既有产品的源码，要求复刻或扩展时：文件树是菜单，不是菜。不要凭记忆或训练数据去重建 UI。而应阅读真实源码：
- 主题与 token 文件：`theme.ts`、`colors.ts`、`tokens.css`、`_variables.scss` 或等价物
- 全局样式表与布局骨架
- 用户点名提到的具体组件

提取精确取值：十六进制色值、间距刻度项、字体栈、圆角半径。粗略近似不是像素级还原。

只挂载目标组件目录或包。排除 `.git`、`node_modules`、`dist` 和锁文件。把整个 monorepo 拖进来只会用无关代码污染上下文、拉低输出质量。

### 既有原生 App 例外（不要提议整体改造平台风格）

当目标是已有连贯视觉方向的既有 macOS / iOS / Android 原生 App 时，不要把整体迁移到更新的平台风格（macOS 26 Liquid Glass、iOS 18 毛玻璃材质、Material You、Fluent Design 等）作为默认改进方案。整体改造读起来像是「我没有具体的设计意图，这是平台给的」。默认做法是在既有方向上做渐进打磨：间距、对齐、hover 与 focus 状态、排版层级、文案收紧、动效时序。只有当用户本轮明确要求，或既有方向已坏到渐进打磨不足以修复时，才提议平台风格迁移。在提议改动之前，先用一句话说明现有方向，以便用户纠正你的理解。

### App 外壳例外（侧边栏 + 主工作区）

如果问题 1 的答案是 App 外壳（Slack、Linear、Notion 这一类），用 tool_resource 加载 `references/design-reference.md`，在继续之前先落实其「App 外壳规则」小节的约束。

### 数据看板例外

如果界面是看板、分析视图或图表密集的界面，还要用 tool_resource 加载 `references/design-data-viz.md`，了解图表选型、数字对齐与产品标杆规则。构建营销页、落地页或通用组件时跳过。

用一句话陈述选定的方向，然后用 tool_resource 加载 `references/design-reference.md`，核对技术栈冲突表。在写第一个组件之前，先点明唯一的 CSS 策略。token 决策（颜色、字体、动效）也在同一个文件里：OKLCH 规则、主题矩阵、字体各小节，以及动效。审美质量评审与生产结构方面：用 tool_resource 加载 `references/design-aesthetic-quality.md`。

在写任何代码之前，把方向总结成三行：
- **视觉命题**：一句话说清气质、材质与能量（例如「高对比墨色字体、粗糙纸感的温暖粗野主义编辑风」）
- **内容规划**：hero -> support -> detail -> final CTA，各一行。对 **App/看板界面**：跳过营销结构，默认走工具模式（定位、展示状态、促成操作），除非明确要求否则不要 hero。
- **交互命题**：2-3 个能改变页面感受的具体动效构想（例如「加载时 hero 文字滑入，滚动时区块标题吸顶而内容在其下滚过，hover 时 CTA 脉动」）

对生产级或多页 UI，把命题扩展成 `references/design-reference.md`（经 tool_resource 加载）里的 9 节 DESIGN.md 骨架（主题、色板、排版、组件、布局、纵深、do/don't、响应式、提示词指南）。对单个组件而言，三行就够了。

## 被问及方案选项时

至少给出 3 个跨越真正不同维度（密度、排版、颜色、布局、动效）的变体。用 tool_resource 加载 `references/design-reference.md`，遵循它的「选项指南」以获得完整的变体框架。仅靠强调色区分的三个选项，不算三个变体。

## 硬性规则

`references/design-reference.md`（方向锁定时已通过 tool_resource 加载）涵盖了全部规则：排版、OKLCH 颜色、动效时序、布局默认值、CSS 模式禁令、无障碍基线，以及复杂度匹配。它们的存在是为了让输出偏离通用默认值，而不是充当一道 lint 关卡：当已确定的方向确实要求打破某一条时，有意识地打破它，并在交接中说明取舍。无障碍基线与 CSS 模式禁令始终不可让步。

## 常见坑

| 发生了什么 | 规则 |
|---------------|------|
| 用 Inter 作展示字体 | 它什么也传达不了。挑一个有性格的。 |
| 三张卡片，相同的阴影、相同的内边距 -- 一个模板 | 如果换掉内容不需要改动布局，就重做。 |
| 没打开浏览器就声称它看起来没问题 | 脑子里正确的代码，在浏览器里可能看着是坏的。打开它。 |
| 选了毛玻璃，却无视移动端约束 | 在低功耗设备上 `backdrop-filter` 开销很大。说明取舍。 |
| 浅色模式 App：白色面板叠在白色背景上，视觉上无从分辨 | 相邻的嵌套表面必须在视觉上有所区别。要么做背景分级（侧边栏与主区域至少 4% 明度差），要么至少用 `0 1px 3px rgba(0,0,0,0.10)` 的阴影。 |
| 通过重设计整个界面来修复一处视觉瑕疵 | 先定位具体的视觉差异，然后做最小的材质、不透明度、几何或排版改动来消除它。 |
| 在两次「丑」的判定之后又第三次重生成图片 | 两次对观感的否决意味着分歧在题材，而不在配色。停止生成，重新对齐这张图要说什么。 |
| 靠加一个设置项或更响亮的控件来解决 UI 噪音 | 先移除误导性的可供性或选定一个安静的默认值 |
| 英文看起来没问题，本地化文本却溢出了 | 交接前测试长单词与本地化字符串，尤其是按钮、标签页、导航与紧凑卡片内部。 |
| 依赖 `…` 截断把文本塞进固定宽度的槽位 | 要保证放得下：压缩格式、截到完整段，或硬截断且不加省略号。指标与标签页脚绝不能尾部截断成省略号。 |
| 多出一个词把一行挤成折行；最后一行只剩一个孤字 | 交接前，扫过每个用户可见文本块，检查濒临折行与孤行状态。通过收紧文案来修，而不是缩小字号；发现一处就意味着扫完整份文档，所有实例都要修。 |

## 输出：审美评审

在重要构建阶段之后与交接时，重读方向锁定阶段写下的视觉命题。如果屏幕上的东西漂向了通用默认值，找出最先被破坏的具体元素（字体、颜色、卡片处理、间距）并在继续之前修好。

在交接总结之前跑这些检查：
- 首屏是否让人一眼认出品牌或产品？
- 是否有一个强有力的视觉锚点（真实图像，而非装饰性渐变）？
- 只扫读标题能否理解整个页面？
- 每个区块是否只承担一个职责？
- 卡片是否真有必要，还是只是默认样式？
- 动效是在改善层级或氛围，还是纯装饰？
- 如果移除所有装饰性阴影，设计是否依然显得高级？
- AI 味测试：扫一遍首屏，找默认套路（反射性字体、紫到蓝渐变、居中 hero 加两个并排 CTA、三张一模一样的卡片、通用顶部导航）。如果任何一项是无意出现的，就修改排版、颜色或布局，直到全部消失。

如果有任一检查不通过，先修。请用户在全宽与 375px 下验证；如果布局在移动端宽度下垮掉，交接前先修。

以这些收尾：
- 审美方向，用 2-3 句话命名并给出理由
- 解释非显而易见的选择：字体、颜色决策、布局逻辑
- 用真实内容替换占位内容的说明

交接之后，停下。
