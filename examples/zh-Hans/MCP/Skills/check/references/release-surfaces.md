# 发布面评审方法

当某个 diff 或发布问题触及下列面之一时，从 `/check` 按需加载。填表用的模板形状在 `project-context.md` 中；本文件负责评审方法。

## CLI 命令面

检查命令契约与安装后运行时行为，而不仅是库层面的测试：help/version、子命令/flag、退出码、stdout/stderr、JSON/schema 输出、TTY/非交互路径、env/配置优先级、shebang/可执行位、PATH shim，以及适用时的包管理器安装路径。

对于变更型 CLI 命令，还要运行安全汇点评审（见 `project-context.md`）：dry-run 或确认路径、操作日志或回滚方案、重试/幂等、信号/部分失败处理，以及针对鉴权提示或真实系统改动的测试模式守卫。对于清理、卸载、裁剪、重置或缓存清除类命令，在批准之前再加两项检查：普通用户能否核实每个被选中的条目是安全的，以及被删除的内容是否可在本地重建、而非一个下载来的依赖或用户数据？如果任一答案为否，就要求更窄的匹配、显式的用户选择，或让该条目保持可见但不具破坏性。

## 打包安装面

验证安装后运行时契约，而不仅源码树：

1. 确定真实用户实际会拿到的安装路径：包管理器、发布归档、marketplace 条目、plugin 源路径，或安装器脚本的默认 ref。
2. 严格按项目文档要求构建或重新生成包，然后检查归档或生成的镜像，确认每一个新脚本、reference、模板、规则、清单与可执行位都在。
3. 当该面可安装时，运行一次隔离安装冒烟：全新的临时 home/config/cache，添加 marketplace 或包，安装该 skill 或 plugin，列出它，并调用最小的命令或入口点，以证明脚本与 reference 能从安装后的路径解析。
4. 过滤生成的镜像与归档中的缓存/噪音文件，例如 `__pycache__`、`*.pyc`、`.pytest_cache`、`.ruff_cache`、`.mypy_cache`、`.DS_Store`、本地日志与截图，除非项目明确要分发它们。
5. 如果网络、鉴权或托管平台工具阻碍了安装冒烟，就把缺失的那一层声明为阻塞项或缺口。不要用清单 JSON、源码测试或一次成功的本地 import 来替代对安装后运行时的证明。

## 返工或已取消发布的闸门

1. 把评审基线锁定到上一个公开的 stable tag 或发布产物，然后一直评审到当前 `HEAD`。不要只评审近期的提交或最新的本地 diff。
2. 记录确切的基线、`HEAD`、脏状态、origin 同步、版本字段、生成产物、发布说明、包内容、CI 与远端分发状态。如果评审中途任何状态发生变化，刷新范围并重跑快速闸门。
3. 按已出厂的风险面评审：用户报告的回归、崩溃或卡死路径、破坏性操作、特权或权限边界、后台 worker、启动或首帧工作、更新源、包内容，以及公开的支持声明。
4. 输出两个发布决策，而非一个：preview 或 beta 能否继续承接用户测试，以及 stable 发布准备能否开始。
5. 每一个结论都必须指名阻塞项、可延后的维护工作、实际运行过的命令，以及运行时或用户冒烟的覆盖情况。仅凭源码测试无法证明一次返工的 UI/原生发布已就绪。
