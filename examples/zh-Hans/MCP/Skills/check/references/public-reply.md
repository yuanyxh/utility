# 公开回复形状（维护者，issue 或 PR）

供分流模式与发布 / 发版续接共用。默认采用此形状，除非目标仓库的 `AGENTS.md` 或 `CLAUDE.md` 与之矛盾。

1. 发布之前，从 `gh issue view` / `gh pr view --json author` 解析出 `@<login>`。
2. **语言:** 当发起者用中文或英文时，与之匹配。如果发起者用日文或韩文，维护者回复一律用英文，除非项目文档另有规定。
3. 以 `@<login>` 开头，加**至多一次**简短致谢（`感谢反馈`、`thank you for the report` 等）。**不要**结尾堆叠致谢（`再次感谢`、`Thanks again`、冗长的客套收尾）。
4. 一到两段简短的话：事实性理由、已发布的内容或被阻塞的内容，不要客套。
5. 点明确切的边界：已发布、已在 `main` 上修复但未发布、nightly/beta/preview 可用、下个版本、不计划处理、重复，或仍需证据。每一句话在发布的那一刻都必须为真：不要在该改动尚未提交时写「已落到 main 上」，除非该状态是在当前轮次核实过的，否则不要写「已发布」「已发版」或「已验证」，也不要暗示一个并未发生的验证步骤（建了分支、跑了产物）。
6. 始终给出一个**与发布或验证挂钩的下一步**：下一个 App Store 或 GitHub release、nightly 升级命令、需要清理一次的缓存路径，或确切说明仍需要哪些信息。
7. 对于诊断包、日志、崩溃转储、截图或本地状态归档，不要要求报告者公开粘贴或附上敏感材料。只索取最少的公开事实，并且只有当公开项目上下文提供了私有支持渠道时才使用它。
8. 更新措辞时，优先**编辑**一条既有的维护者评论（`PATCH /repos/{owner}/{repo}/issues/comments/{comment_id}`）；避免删除再重发，除非旧文本必须从历史中消失。

## 关闭时

关闭评论是给报告者的答复，不是调查过程。说明修复状态、它会从哪个通道到达、何时到达，然后停笔；根因、文件名与推导过程属于提交。一条需要滚动才能读完的回复，无论结构多好，都太长。

只有当修复已发布、已在最新 release 中可用、报告无效、报告重复，或维护者明确要求关闭时才关闭。否则留开，并附上下个版本的确认。
