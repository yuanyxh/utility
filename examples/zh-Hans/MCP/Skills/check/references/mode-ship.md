# 发布价值与发布续接

从 `check` 的模式选择加载，用于「这值不值得发版」，以及提交 / 推送 / 发布 / 打 tag / 关闭 issue 的续接。发布延展评审；它不替代评审。

## 发布价值分析

当用户问「深入分析 X 是不是值得发新版本」「这是否值得发一个新版本」「值不值得发版」或类似问题时激活。

对自上一个已发布 tag 以来的每一次提交进行分类（tag 是基线，而不是本地的 VERSION 文件），然后输出：

- **提交小结**：自上次发布以来 N 个 feat、N 个 fix、N 个 chore
- **结论**：发布 / 跳过（一行）
- **建议的版本号跃升**：patch（仅修复）、minor（有 feat）、major（破坏性变更）
- **关键风险**：一句话说明这批中最大的风险

如果结论是「发布」，提供转入 Ship 模式。

## 发布 / 发版续接

当用户在一次改动就绪后要求提交、打 tag、发布、发表、推送、回复 issue/PR 或关闭 issue 时激活。

本模式延展评审；它不跳过评审。在任何公开或不可逆的动作之前：

1. 从公开项目上下文中提取发布规则：README、清单、CI 工作流、发布说明、包脚本、changelog，以及当前线程中用户的明确指令。
2. 从 `references/project-context.md` 填入 Release Gate 2.0 矩阵。用 `python3 <skill-base-dir>/scripts/release_gate.py --root <project>`（工作区状态、远端同步、tag 基线、版本字段同步、changelog 提及）为确定性的行提供初始数据，并把它的 status 行粘贴为证据；其余行（生成产物、包/归档内容、发布资产、registry/appcast/CI、公开 issue/PR 状态）仍属需判断的项，各附证据。
3. 核实生成或打包的产物、版本字段、发布说明、包内容与必需产物是否同步。当生态提供 dry-run 命令时优先使用。起草发布说明或更新源文案时，遵循 `/write` 及其 release-note 模式；对于中文文案，在首次起草之前就加载它的中文发布说明规则，而不是等到有人抱怨语气之后 —— 带着翻译腔的中文说明是缺陷，不是打磨项。
   起草发布说明之前，先读仓库上一次已发布的 release（对最新 tag 运行 `gh release view`），把它的标题约定、条目数量、单条长度与语言布局当作硬模板；只替换内容，绝不另创格式。
   生成的可交付物包括被跟踪的归档、被忽略的 dist 文件、appcast、站点/下载文案、registry 包、校验和与发布资产。如果项目文档要求它们，即使它们被 git 忽略，也要显式地重新生成、检查并暂存或上传；不要从仅源码的测试推断就绪。对于远端资产，优先下载或回读已发布的产物，比对条目、校验和或清单内容；仅凭发布页文本、文件大小或工作流成功，都不构成产物证明。
   如果项目有 preview、beta、nightly、stable 或 App Store 通道，明确说出是哪个通道。不要用 preview 或 beta 产物来声称 stable 发布就绪；当请求的通道仅为 preview 时，不要碰 stable 的 appcast、registry 或下载面，除非项目文档要求。
   在断定什么是「已上线」之前，按部署面给每个改动分类：打包在产物内的代码（app 二进制、随包分发的 CLI、发布归档）只有在下一个版本才到达用户，而站点、serverless 函数、CDN 配置与基础设施在默认分支更新时即自动部署。同一批改动可以在第一个面上尚未发布，而在第二个面上早已在生产。分别陈述每个面，不要让「还没发布」这句话去覆盖自动部署的代码。
4. 只提交预期内的文件。保留无关的脏改动，串行化 git 操作，避免索引锁或重叠的 add 破坏工作流，并在推送前重新核对 HEAD/status，以免并发的 agent 或维护者提交被卷入你的发布动作。
5. 只有当用户显式批准该动作时，才推送、发表、打 tag 或创建 release。如果鉴权、OTP、CI、registry 或网络状态阻断了操作，暂停并报告确切的阻塞项。
6. 对于 issue/PR 续接，在发布之前先用托管平台的读取命令确认条目身份。在 GitHub 上，使用 `gh issue view` 或 `gh pr view`；在其他托管平台上，使用项目文档或当前请求所指的 CLI/API。维护者回复模板（@ 提及、单次致谢、事实、明确的下一版本或验证步骤）及其关闭判据，参见 `references/public-reply.md`。
7. 对于 GitHub 发布表情续接，只有当项目上下文或当前线程要求时才做。在 release 存在且必需资产已核实之后，从 tag 解析出 release id，用 `gh api` 或可用的 GitHub 工具把每一个正向的发布表情 POST 到 `repos/<owner>/<repo>/releases/<id>/reactions`，并重读表情以确认。正向发布表情为 `+1`、`laugh`、`heart`、`hooray`、`rocket` 和 `eyes`。
8. 网络或 API 失败之后，重读最终状态，而不是假定成功或失败。

### 返工或已取消发布的闸门

当一个 release 候选被取消、一个 preview 或 beta 经历了反复的修 bug 折腾，或用户问一个延期的发布是否终于安全时，激活此闸门。加载 `references/release-surfaces.md`（Reworked Or Cancelled Release Gate）：从上一个公开的 stable tag 一直评审到 `HEAD`，按已出厂的风险面进行，并输出两个决定：preview 是否继续承接用户测试，以及 stable 发布准备是否可以开始。

结论以明确的 go / no-go 打头（发布，或指名阻塞项），随后是具体的已出厂状态：提交 hash、tag、release URL、registry/版本结果、已推送的分支、发布资产状态、发布表情状态、issue/PR 状态，以及任何剩余阻塞项。不适用的字段略去。
