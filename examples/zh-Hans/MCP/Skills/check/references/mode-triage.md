# 分流模式（issue / PR 队列）

当请求是 issue/PR 分流时，从 `check` 的模式选择加载。共享的评审面（范围、硬性阻断、自动修复、专家评审、验证、收尾签署）仍依 `SKILL.md` 适用。

当用户提到：issue、PR、「全部评审」、triage、「batch」或「批量处理」时激活。跳过 diff 流程，改跑本模式。

**行动优先规则:** 处置明确的条目（已修复、重复、已发布）立即行动，不写分析段落。分析截图或图片时，在一条消息里说明你看到了什么以及建议的动作。只有当处置确实含糊时才询问用户。

**合并请求分类:** 当一个 issue、PR 或支持线程包含多项诉求时，行动前先拆分：核心 bug、既有能力、外观偏好与范围外请求。只修复或关闭已验证的核心 bug；对既有能力以当前路径作答；对仅外观与范围外的诉求，推迟或婉拒，而不是把整份报告当作一张待办清单。

**状态回答顺序:** 对「都解决了吗」「这是否修好了」「这准备好没有」或类似的状态询问，按此顺序回答：代码或提交状态、分支或 CI 状态、发布产物或 registry 状态，然后是公开的 issue 或 PR 状态。不要混淆「已在 main 上修复」「预发布可用」「下个 stable 版本」与「已经发布」。

**流程:** 从公开上下文识别项目的 issue/PR 托管平台，并使用该平台的 CLI/API；如果不存在，停下并报告缺失的集成，而不是假装 GitHub 命令适用。对每个未关闭的条目，对照项目的发布边界检查当前状态：最新的公开 release、main 分支、preview/nightly/beta 通道、registry/appcast，以及目标 issue/PR 状态。已在某个公开 release 或已记录的预发布通道中：以那条确切的升级路径关闭它。已在 `main` 上修复但未发布：回复「已修复，等下一个版本 release」，并且只有当项目惯例或当前用户请求允许「已修在 main 上」即关闭时才关闭，否则留开并附上下个版本的说明。尚未修复：分析并行动。如果可行就立即修复（`fix: closes #N` 提交）；对有效但未发布的条目予以确认并留开；对无效条目给出一两句话的理由并关闭。

在活跃队列中给出最终结论之前，再刷新一次 issue/PR 列表，并重读运行期间发生变化的任何条目。如果证据不完整，扣住该条目，而不是凭猜测关闭它。

**PR 处理:** 每个 PR 恰好得到三种处置之一，并在请求授权之前在分析输出中指名：按原样合并、把修复推送到贡献者的分支后再合并，或作为「不计划处理」关闭。「按原样不可合并」却不指名「在你的分支上修复」这一选项，是不完整的分流，而且是最常被跳过的一种，因为补丁的缺陷恰恰是它最显眼之处。如果 PR 的方向被接受但补丁需要改动，优先把维护者的修复推送到贡献者的 PR 分支，然后合并该 PR。先检查 `maintainerCanModify`，然后在推送前立即确认推送远端、目标分支与当前 HEAD，以免覆盖贡献者的工作或把维护者的修复推到错误的仓库。如果不允许编辑分支，请贡献者开启维护者编辑，或推送所需的修订；只有在时序或发布安全要求时才回退到一次独立的维护者提交，并在 PR 中说明这一点。只有当方向被拒绝、不安全、不再需要或明确不属于项目范围时，才不合并而关闭。不要悄悄把一个被接受的 PR 吸收进 `main` 然后关闭它。

**公开回复形状:** 加载 `references/public-reply.md` 获取完整模板（@ 提及、单次致谢、事实性段落、下一版本步骤、编辑规则、关闭判据）。Ship 模式使用同一模板；该文件是唯一来源。

**收尾签署行（附加到标准收尾签署之后）:**
```
triage:           N reviewed, N closed, N deferred
```
