# Check：发布前先审查

首行以内联方式加 🥷 前缀，不要单独成段。

> 注意：`/review` 是 Anthropic 内置的 PR 评审插件命令。Waza 改用 `/check`（或别名 `code-review`）。不要在本 skill 内再次触发 `/review`。

读取 diff 并找出问题。评审、审计、分流、发布就绪类请求都只做报告；只有当本轮明确要求修复、更改、实现或优化时才动手改代码。「完成」的含义是：请求的评审面已被覆盖，且每一条验证声明都来自本次会话。

## 结果契约

- 结果：一份基于当前 diff、项目上下文与实时证据的评审、发布决策或维护者动作。
- 完成条件：发现、修复、已发布状态或阻塞项，都附带证明它们的命令、产物或远端状态。
- 证据：工作区状态、diff、公开项目文档、清单、CI、包内容、发布或 registry 状态，以及当前命令输出。
- 输出：先给简洁的发现，再在适用时给出验证与发布状态小结。多步骤或发布动作类的运行以一份完成台账收尾（已完成 / 不适用 / 剩余），绝不用一段叙事让用户追问「是不是都做完了」。
- 授权：只读意图可以检查工作区与远端状态，但不得编辑文件、应用自动修复、提交、推送、发布、评论、关闭、合并或切换分支。每一次写入或公开动作都需要当前轮次的授权，除非用户明确授权了一个包含该动作的具名批次。

## 工作区安全预检

在任何评审、分流、发布、发版或 PR 操作之前，先用以下命令读取当前工作区：

```bash
git status --short --branch -uall
```

把已修改、已暂存、未跟踪的文件都当作用户的工作。你可以读取它们并把它们纳入评审面，但未经用户在当前轮次的明确批准，不得移动、隐藏、覆盖、清理或丢弃它们。

不要把这些命令当作默认的评审或 PR 准备步骤：`git switch`、`git checkout`、`git reset --hard`、`git clean`、`git stash -u`、`git stash --include-untracked`、`git stash -a`、`git stash --all`，或 `gh pr checkout`。如果确实需要切换分支或清理，停下来，就那一项具体操作征求用户同意。

不要通过把未跟踪文件、生成文件、截图或本地临时文件移入 `/tmp` 或其他暂存目录来「保护」用户的工作。把别人的 WIP 移出检出一事，与把它 stash 起来属于同一类干扰。如果生成、打包或验证需要一棵干净的工作树，请从某个已知提交另建一个 worktree，只把你拥有的产物或补丁拷回当前检出。

在脏工作区或多 agent 检出的提交或推送续接中，暂存之前先记录 `git rev-parse HEAD`。提交前立即重新读取 `git status --short --branch -uall` 与 `git rev-parse HEAD`，推送前再次读取。如果 HEAD 变了、出现了未知提交，或工作区在你预期之外的文件上发生变化，停下来报告这一不一致，而不是 rebase、重新提交或推送。

做 PR 检查时，优先使用不切换当前工作树的命令：`gh pr view`、`gh pr diff`、`git fetch origin pull/<n>/head:refs/tmp/pr-<n>`、`git merge-tree`。

## 模式选择

挑一个与用户意图相符的模式，然后用 tool_resource 加载它并在动手前完整通读。模式叠加在下方共享的评审面（范围、硬性阻断、自动修复、专家评审、验证、收尾签署）之上，后者在每个模式下都适用。只有当某一行匹配时，才用 tool_resource 加载对应模式文件；默认评审路径不需要任何模式文件。

| 用户意图 | 模式 |
|---|---|
| 「按这个计划实现」、移交 `/think` 的输出 | [计划执行模式](#计划执行模式) |
| diff 或 PR 就绪,「review」「看看代码」「合并前」 | 默认评审（从 [获取 Diff](#获取-diff) 开始） |
| 「看看 issue」「评审 PR」「triage」「批量处理」 | 用 tool_resource 加载 `references/mode-triage.md` |
| 「这个值不值得发版」「值不值得发版」 | 用 tool_resource 加载 `references/mode-ship.md`（发布价值分析） |
| 「commit」「push」「publish」「release」「关闭 issue」「发布表情」 | 用 tool_resource 加载 `references/mode-ship.md`（发布 / 发版续接） |
| 「audit」「项目体检」「项目评分」「给项目打分」「深入分析项目代码」「scorecard」「linus review」 | 用 tool_resource 加载 `references/mode-audit.md` |
| 文档、PDF、散文评审 | 移交 `/write`（见 [文档评审](#文档评审)） |

在任何模式之前，先执行 [项目上下文提取](#项目上下文提取)，并在记忆在范围内时执行 [持久上下文预检](#持久上下文预检)。

## 项目上下文提取

这是 Waza 公开、独立的代码评审能力。它不应依赖私有的机器路径或未公开的项目指令。

评审之前，从仓库上下文中提取项目约束：

1. 读取 diff，识别变更涉及的编程语言、框架、清单、生成产物、发布文件与 CI 工作流。
2. 只按需检查公开项目文件：README、存在时的 AGENTS/CLAUDE 指令、包清单、lockfile、构建配置、测试配置、工作流文件与发布说明。
3. 把这些发现压缩成评审上下文：验证命令、受保护或生成的文件、发布产物、领域风险与公开回复规则。
4. 当项目上下文与本 skill 有重叠时，采用更严格的那条规则。
5. 如果项目文档或 CI 指定了某个验证命令，优先采用它，而非自动探测。

上下文的形状参见：用 tool_resource 加载 `references/project-context.md`。

对于发布或维护者工作，还要从 `references/project-context.md` 填入 Release Gate 2.0 矩阵（用 tool_resource 加载它）。它覆盖评审基线、脏/已暂存/未跟踪状态、最新 tag、origin 同步、版本字段、生成产物、包/归档内容、发布资产、registry/appcast/CI，以及公开 issue/PR 状态。矩阵证据缺失是「可以发布」这一结论的阻断项。

## 持久上下文预检

当持久上下文在范围内时，以及在任何持久上下文成为持久规则之前适用的脱敏闸门，用 tool_resource 加载 `references/durable-context.md`。

针对 `/check`：当前 diff、CI 与远端状态优先于记忆。持久记忆可以解释用户意图与偏好的续接方式，但公开项目规则仍来自 README 文件、清单、CI 工作流、发布文档，以及当前线程中的明确指令。绝不要把私有记忆当作公开项目要求来引用。

## 计划执行模式

当用户消息以「Implement the following plan」「按计划实施」「按照计划」「整」「可以干」「直接改」开头并跟有一段计划正文，或链接到 `/think` 的输出时，激活此模式。

在此模式下，不要做代码评审。改为：

1. 说明正在执行的是哪份计划（第一个标题或摘要行）。
2. 检查明显的仓库漂移：运行 `git status --short --branch -uall`，扫一眼那些与计划相矛盾的已改动文件。如果漂移使计划变得不安全，指出具体冲突并停止。
3. 所有条目完成后，运行项目的验证命令。
4. 如果项目上下文或当前线程表明要「先评审后发布」，自动转入 mode-ship（用 tool_resource 加载 `references/mode-ship.md`）。

## 默认续接（先评审后发布）

当项目的 `AGENTS.md` 或当前线程明确要求「评审后提交」「绿了就发」或类似内容时，用 tool_resource 加载 `references/mode-ship.md`，并在一次干净的评审之后直接从评审转入发布流程。不要再问。动手前先声明「进入发布流程」。

## 获取 Diff

获取当前分支与基线分支之间的完整 diff。如果已经在基线分支上，询问要评审哪些提交。

## 范围

度量 diff 并划分深度：

| 深度 | 判据 | 评审者 |
|-------|----------|-----------|
| **Quick** | 少于 100 行，1-5 个文件 | 仅基础评审 |
| **Standard** | 100-500 行，或 6-10 个文件 | 基础 + 条件性专家 |
| **Deep** | 500 行以上、10 个以上文件，或触及鉴权/支付/数据变更 | 基础 + 全部专家 + 对抗性审查 |

动手前先说明深度。

对于 **Standard** 与 **Deep** 深度，在专家审查之前用 tool_resource 加载 `references/persona-catalog.md`；它定义了哪些专家被激活。这是强制步骤，而非条件步骤。

静态内容 diff 即使触及多个生成文件也可以保持 quick：版本字符串、日期、发布文案镜像、sitemap 日期，或一一对应的本地化文案改动，通常需要逐行回读加 grep 一致性核对，而非一整队专家。只有当 diff 改动了逻辑、生成规则、公开分发行为，或超出字面文本替换的面向用户的语义时，才升级。

## 我们建的是被要求的东西吗？

读代码之前，先检查范围漂移：diff 与所述目标是否吻合？标注：**on target** / **drift** / **incomplete**。

同时检查外科手术级的可追溯性：每一个改动的文件与每一个新增的公开面都必须能追溯到用户所述的目标。如果某个文件、依赖、配置开关、抽象、生成产物、工作流权限或发布行为无法用一句话从请求中解释清楚，就先标注为 drift，直到证明其必要。

漂移信号（示例，非穷尽 —— 命中任意一条就足以标注 drift）：
- 某个改动的文件与所述目标毫无关联
- 当目标是修 bug 或做功能时，diff 里却包含纯粹的重构（重命名、格式化、结构调整）
- 出现了目标未提及的新依赖
- 与目标无关的代码被删除或被注释掉
- 引入了目标并不需要的新抽象或辅助函数
- 一次可维护性、评审或清理改动悄悄加入了面向用户的 UI、默认配置、工作流权限或发布行为

## 同类缺陷修复的完整性

当 diff 修复了某一类 bug 中的一个实例（一处缺失的校验、一个错误的选择器、一个差一错误、一把缺失的锁）时，同样的形状往往还存在于别处。提取该模式的签名，在全仓库 `grep -rn`（排除生成目录），确认同类的实例也一并处理了。列出任何未清扫的同类项：当它带有相同风险时标记为硬性阻断，风险较低时作为建议。更深入的清扫手册参见 hunt 的 Scope Blast Mode。

## 为复现型缺陷预留可测试接缝

当 diff 修复的是已经复现过的视觉、布局、时序或有状态 UI 缺陷（同一区域此前坏过，或这个修复读起来像「调数字直到看起来对」）时，仅凭代码改动会让回归卷土重来：逻辑与可变的渲染或 UI 状态纠缠在一起，以至于无处可对其断言。除非修复把这一判断抽成一个纯函数 —— 输入进去、值出来，没有可变接收者 —— 并对被违反的不变量（宽度绝不塌缩为零、命中区域保持半开、偏移保持在界内）做单元测试，否则就把该修复标为不完整。「跑一遍 app 验证过」只证实这一个实例；只有钉住不变量才能挡住下一个。把这一条留给那些会复现、或运行时检查看不见的类别；不要为已有直接覆盖的一次性逻辑要求接缝。如果不存在诚实的接缝 —— 唯一能断言的地方位于一个从不触发调用点处真实故障的浅接口之后 —— 不要为了满足闸门而伪造一个空洞的测试。把「没有正确的测试接缝」记为一项架构发现并把它摆上台面：缺失的接缝本身就是那个缺陷。

当缺陷只是「一个错误的决定」时，纯函数是正确的接缝。当缺陷是「未来的调用点会绕过它」时，纯函数就是错误的接缝：一个上提到共享辅助函数里的守卫，仍然只保护那些经由它路由的调用者，而下一个贡献者会在没有它的情况下新增第十一个调用点。对这类缺陷，能守住的守卫是一个对源码树本身做断言的测试 —— 枚举这个高危原语的所有调用点，任何跳过包装的调用点即失败，或任何在显式白名单之外新出现的原始模式即失败。它跑在常规测试套件里，不需要运行时，把「总得有人记得」变成一次构建失败。把它留给那些「忘记」既无声又昂贵的原语（无边界的对外命令、直接删除、裸特权提升），并把白名单留在测试里，让每一条豁免都是一行经过评审的代码。

## CLI 命令面

当 diff 触及 CLI 入口点、安装器、补全、配置/env 处理、包包装器，或诸如清理、更新、卸载、迁移、缓存清除这类变更型命令时，用 tool_resource 加载 `references/release-surfaces.md`（CLI Command Surface）并执行其清单，然后在收尾签署之前，从 `references/project-context.md`（同样用 tool_resource）填入 CLI Command Surface 模板。核心立场：验证命令契约与安装后运行时的行为，而不仅是库层面的测试，并把每一个变更型命令都当作安全汇点。

终端输出是一个被渲染出来的面。改动面向 CLI 的文本、间距或布局后，要重新运行命令并读取真实输出，再声称完成；编辑字符串不等于看到屏幕。

## Skill、Plugin 与打包安装面

当 diff 触及 skill、plugin、marketplace 条目、安装器、包白名单、包清单、生成的镜像或已发布的归档时，用 tool_resource 加载 `references/release-surfaces.md`（Packaged Install Surface），并通过它的五个步骤验证安装后运行时契约：真实用户安装路径、重建后的包内容、隔离安装冒烟、噪音过滤，以及冒烟无法运行时的显式缺口。清单 JSON、源码测试或一次成功的本地 import，永远不能替代对安装后运行时的证明。

## 硬性阻断（合并前必须修复）

示例，非穷尽 —— 任何在未评审下合并就可能造成不可逆损害的 diff 都要标记。

- **不允许未经证实的声明。** 除非 shell 输出就在本轮的记录里，否则不要写「我验证了 X」「我跑了 Y」「测试通过」或「这修复了 Z」。如果你只是在没有运行的情况下推理行为，请说「基于阅读代码」，而不是「我验证了」。收尾签署里每一条验证声明都必须指向一条本次会话中真正运行过的命令。
- **引用事实源之前先重新读取。** 在把行号、脏文件数量、分支领先/落后状态、回退行为、语言覆盖情况或发布产物状态写进交接或评审报告之前，先在本轮重新读取源（`git status`、`git diff`、文件 `Read`、`rg`、命令输出）。更早的聊天上下文、先前的 agent 笔记，以及你自己的回忆，默认已过时。内联引用验证路径（`per current Read of <file>` / `per git status this turn`），让评审者知道哪些事实是有锚点的。
- **对捕获输出做字符串匹配**：当 diff 依据错误消息或命令输出做分支判断或 grep 时，先探测该字符串在运行时实际持有什么，再批准。以 `stdio: 'inherit'`（或任何未捕获的管道）启动的子进程会把诊断信息留在终端，而 `error.message` 只持有命令行，于是匹配器悄悄匹配到了命令本身，而不是输出。优先使用调用方本已持有的结构化事实（退出码、构建目标），而非重新解析一个字符串。
- **魔法等待耦合**：用固定的 `sleep`、`asyncAfter`、`setTimeout` 或「应该够了」的超时，来代替一次未被观测的异步完成；或者把动画、轮询、进度步骤绑定到帧数或固定时长，而非墙钟状态。它在作者机器上通过，在慢 CPU、120Hz 显示器或被代理的网络下就坏。标记它：让下一步由真实的完成信号驱动（回调、导航完成、帧变化、状态标志），并保持时序与机器、帧率无关。
- **破坏性自动执行**：任何被标为「安全」或「自动运行」、却会修改用户可见状态（历史文件、配置、偏好、已安装软件）的任务，都必须要求显式确认。
- **源码与分发不同步**：源码改动在上游隐含的一切，都必须在宣告完成之前被重新生成、跟踪、上传且版本一致：生成或打包的产物已重建并纳入，发布说明或工作流中提及的每一个产物都已实际上传，每一个新增的辅助模块、reference 文件或脚本都存在于构建出的归档中，以及版本字段在清单、包元数据、changelog、tag 与 lockfile 之间保持同步。
- **验证器失败层级不清**：如果验证器在断言之前失败，或因缺失可选依赖、引导噪音、构建服务瞬时崩溃、模拟器不可用或工具安装而失败，要区分是环境搭建失败还是产品失败。只有在有新证据或更窄的环境时才重试。在预期的测试体或产物检查真正运行之前，不要说仓库坏了。反过来是同一个阻断：一个未经真实路径就通过的验证器 —— 一个被跳过但仍打印 OK 的可选依赖任务、一个提前返回导致输出为空从而使「空即为真」的断言通过的函数、一个报告已修复却从未打开过的渲染 —— 是空洞的绿。只有当至少一个未被跳过且非空的用例真正走过该路径、且断言在空输入上会失败时，一次通过才算数。
- **仅凭清单的安装证明**：如果 diff 改动了 skill、plugin、安装器、marketplace 条目、包包装器或可安装归档，元数据与源码测试是不够的。要么在隔离环境里通过真实用户路径构建或安装，要么把安装/运行时层标为未验证。
- **diff 中的未知标识符**：diff 中引入的任何在代码库中不存在的函数、变量或类型都是硬性阻断。在写或批准任何引用之前先 grep：`grep -r "name" .` —— diff 之外没有结果 = 不存在。
- **没有过度删除审计的合并整理**：一个自称目的是简化、合并或精简文字（规则、skill、文档、指引）的 diff，其删除内容要被当作 diff 回读，每一条都归类为「已并入 X」「与 Y 冗余」或「移除了行为」。被移除行为的条目要列给维护者，绝不能被吸收进一行「已简化」的小结里。删除量不是一次好整理的证据，而驱动这类 diff 的精简规则本身没有对等的制衡，所以审计只能来自评审。
- **没有证据的死代码或 YAGNI 删除**：任何「零调用者」或「未使用」的断言都必须遍历整个仓库核对，包括顶层入口点、文档、测试、生成的派发表、脚本、CI、包白名单、包清单与动态查找模式。把子 agent 或工具的报告当作线索，而非证据。删除之前，批量 grep 所有候选，把仅测试引用与生产/运行时引用分开归类，并追查那些可能会一并变成孤儿的手写变量或数据表。如果某个文件只是被错误地通过某个包、归档或插件镜像暴露出来，那就收紧那个分发面及其测试，而不是删掉这个开发工具。如果 grep 的范围不完整，就不要删。
- **注入与校验**：系统入口点处的 SQL、命令、路径注入。硬编码、记入日志、提交或复制进公开文档的凭据。
- **依赖变化**：package.json、Cargo.toml、go.mod、requirements.txt 中意外的新增或版本跃升。标记任何 diff 显然不需要的新依赖。反过来也是一项发现：一个在全仓库零 import 的已声明依赖或已链接 SDK 要上报给维护者，而非悄悄移除（它可能是为某个即将到来的功能做准备，而且未使用的 analytics/telemetry SDK 仍会拖累应用审核与隐私清单）。移除需要维护者在当前轮次的首肯、一份证明零引用的 grep，以及之后的一次完整构建。
- **安全汇点**：破坏性文件操作、shell 或 AppleScript 构造、cwd/路径/symlink 穿越、审批或沙箱边界变更、签名/appcast 流程，以及鉴权提示，都需要对校验、回滚与用户确认行为做显式评审。
- **恢复之前先审计**：当 diff 重新加入一个近期历史移除过的符号、字符串、资源或配置字段时，grep diff 的其余部分与主分支，确认还有什么仍在使用它。一个提及该符号的规则文件不是它仍存活的证据。如果只有一个对等测试引用它，那么该规则已过时、这次恢复是错的；拒绝这次恢复并标记那条过时规则。尤其可疑的是：重新加入一个先前的提交有意删除的 enum case、xcstrings 条目、字典键或资源文件。
- **有意为之的分歧被规范化**：某个面故意打破一条内部模式 —— 省略一个共享步骤、走一条同类都避开的条件分支、留下一处不对称 —— 以规避某个已知缺陷，随后一次清理「顺手」把它重新规整为一致，又把 bug 引了回来。在把一个异类统一到它的同类之前，读一读创建它的那条注释或提交，确认它防范的那个缺陷在你的改动之后仍然存活。
- **破坏性汇点中的宽泛匹配器**：任何向破坏性汇点喂入递归、批量删除、遍历、ID 前缀通配或兜底正则分支的 diff，都要逐行评审三件事：每个分支中匹配器的宽度（兜底路径常退化成宽泛的 glob）、新入口点的受保护路径覆盖，以及任何被绕过的用户确认步骤。要按形状把关，而非按作者：最昂贵的实例往往由熟悉代码库的维护者写出，那里删除目标是靠把显示名、厂商前缀或用户提供的标签字符串拼进一个路径而得，而一个仅仅共享该 token 的邻近项也被一并删掉。问一问授权这次删除的最窄证据是什么；一个精确的标识符或精确的路径可以通过，一个前缀或一个常见词则不行。当 PR 很可能是 AI 生成时进一步提高门槛，不要批准「看起来没问题」。守卫放在哪里与它的宽度同等重要：放在调用点上的检查只保护那一个调用者，所以更应放在删除原语本身内部。
- **同一个值有两处推导**：同一个分类、排序、阈值、计数或资格规则，在两处被独立计算（一份摘要与它所概括的列表、排序与它排序的控件、一个评分与它旁边的诊断文本、一个预览计数与执行器的谓词）。它们在写下那天一致，在对任一侧的第一次改动时就漂移。当 diff 增加了第二处推导时，要求单一事实源：把规则上提为一个共享常量或纯函数，让两侧都读它。当 diff 改变了既有的一对中的一侧时，grep 另一侧并确认它也跟着变了。两个描述同一事物的数字之间出现用户可见的不一致，正是这一条所防范的症状。
- **测试断言在一个生产从不运行的面上**：一个钉住没有任何调用路径能到达的辅助函数的测试，或断言某个命令/配置字符串的字面源码形状的测试，会在发布路径已坏时依然保持绿色，并把坏掉的形态钉为正确，从而挡住正确的修复。它与上面的「空洞的绿」相关，但是相反的失败：那里验证器跳过了真实路径，这里它走了一条并非真实的路径。评审与修复一同加入的测试时，问一句：它在未修复的代码上会失败吗？它所断言的入口点是不是用户真正到达的那个？如果任一个的答案是「否」，这个测试是一项发现，而不是覆盖。
- **为先前未曾发布的特性写的迁移代码**：当底层的偏好 / schema / 特性是在同一个版本里才引入时，拒绝迁移脚手架、按版本分级的默认值，或「把旧键带过来」的逻辑。`git show v<last-release>:<path>` 就是闸门：如果该键在上一 tag 中不存在，就无需迁移；直接发布默认值。为一个从未发布过的键添加的迁移代码是「出生即死」的复杂度。

## 发现质量闸门

在把任何发现写进报告之前，先过这道闸门：

**报告前自检（四个问题，每条发现都必须通过）：**
1. 我能引用精确的 file:line 吗？
2. 我能描述触发坏结果的具体输入或状态吗？
3. 我读过上游调用者 / 下游消费者，而不只是孤立地看那个函数吗？
4. 严重程度站得住脚吗？一位资深评审会在真实的 PR 里以这个级别提出它吗？

如果任一答案是「否」，就丢弃这条发现或把它降级为建议。含糊的发现会训练读者忽略真正的发现。

**一次干净的评审就是一次有效的评审。** 不要为了给这次调用一个交代而制造发现。零发现加上一段说明过的评审面，就是一份完整的输出。用低置信度的噪音给报告灌水，比什么都不报更糟。

**HIGH 与 CRITICAL 需要三样证据：**
1. bug 所在的精确 file:line。
2. 具体的触发条件：什么输入、状态或序列会产生坏结果。
3. 为什么既有的守卫（校验、类型系统、上游捕获、框架默认值）并未已经阻止它。

无法给出全部三样？降级为 MEDIUM，或丢弃。「这在某种条件下*可能*会坏」不是 HIGH。

## 知识同步

评审完 diff 之后，检查它是否引入了尚未被项目文档捕获的不变量：

- 新的安全闸门或路径守卫规则 → AGENTS.md
- 新的 UI 约束（布局规则、动画、overlay 注册） → `.claude/rules/*.md`
- 新的部署/发布步骤或产物 → AGENTS.md 或 `docs/`
- 新的跨文件同步要求（enum ↔ HTML 锚点、Swift 键 ↔ xcstrings） → AGENTS.md
- 一次性的评审报告或诊断快照不应原样成为持久文档；把其中稳定的规则提取进 AGENTS/CLAUDE/rules/references，并从提交里去掉这份过时的报告。

### 快照报告的处置

把评审报告、评分卡与诊断快照当作证据，而非事实源文档。在批准一份之前：

1. 重新读取该报告所指的当前 diff 或仓库面。如果断言已过时，就把该报告排除出提交，或把它改写为一条稳定的规则。
2. 把项目专属的命令、路径、受保护区、发布仪式与安全约束保留在该项目的公开上下文中。不要把它们提升进 Waza。
3. 只把可迁移的评审行为提升进 Waza：例如「就绪前检查未跟踪文件」「检查生成的包内容」或「把一次性报告转化为不变量」。

如果发现了不变量，要么把文档更新作为 `safe_auto` 应用（当不变量从 diff 中清晰可见时），要么在收尾签署里把它标为 `doc debt`。当没有新的不变量时，收尾签署写 `doc debt: none`。

## 专家评审（仅 Standard 与 Deep）

先用 tool_resource 加载 `references/persona-catalog.md`；它决定哪些专家被激活。对 Standard 与 Deep 而言，这次加载是强制的、无条件的。然后，当环境具备 agent 或子 agent 能力时，并行启动所有被激活的专家，每个都拿到完整 diff 与自己的角色简报。如果不存在并行评审能力，就在同一会话里顺序运行各专家审查。

合并发现：当两位专家标记同一处代码位置时，保留更高的严重程度，并注明跨评审者的一致。不同代码位置上的发现永远不是重复项，即使它们共享一个主题。

每一位专家的发现都是待验证的主张，而非可直接据以行动的事实。对于 HIGH 与 CRITICAL 主张，当 agent 能力允许时，为每条发现派生一名独立的怀疑者，其唯一职责是依据真实代码反驳它；一条被怀疑者在直接阅读后反驳的发现会被丢弃或降级，无论它出自哪个角色。没有这个能力时，你自己跑一遍怀疑者审查：在本轮重读被引用的代码，确认该主张真实且活跃、未在别处已被处理、并非有意为之、也不是一个被贴上真实 bug 标签的潜在风险。并行评审者会因基于名称的推断和不完整的上下文而过度报告；丢掉那些在直接阅读后消解的，并在把任何东西路由到自动修复或收尾签署之前引用验证路径。

在给出全范围结论之前，为每一次被委派的评审对账一份完成台账：被指派的范围、返回的状态、未覆盖的剩余部分。等到每一位活跃的评审者都返回，或把其范围标为未评审。当任何评审者或必需验证仍在进行时，绝不要说「全部读过」「完成了完整审计」或「没有问题」。

## 自动修复路由

| 类别 | 定义 | 动作 |
|-------|------------|--------|
| `safe_auto` | 无歧义、无风险：拼写错误、缺失的 import、风格不一致 | 仅在显式写入授权后应用；否则报告它 |
| `gated_auto` | 很可能正确但会改变行为：空值检查、新增错误处理 | 归入一个用户确认块 |
| `manual` | 需要判断：架构、行为变更、安全权衡 | 在收尾签署中呈现 |
| `advisory` | 仅供信息参考 | 在收尾签署中注明 |

在获得显式写入授权后，先应用 `safe_auto` 修复，再展示 `gated_auto` 确认块。在仅报告模式下，不要改动工作树。

## 对抗性审查（仅 Deep）

「如果我想通过这个特定 diff 破坏这个系统，我会利用什么？」四个角度（先用 tool_resource 加载 `references/persona-catalog.md`）：假设违反、组合失效、级联构造、滥用场景。当存在 agent 能力时，把四个角度作为并行 agent 运行，彼此看不到对方的发现：来自独立角度的汇聚会提升置信度，而孤立的发现要接受与专家主张相同的逐条怀疑者验证。抑制置信度低于 0.60 的发现。

## 平台操作

使用与项目匹配的平台工具。对于 GitHub 项目，优先用 `gh` 或可用的 GitHub 集成，并在合并前确认 CI 通过。对于非 GitHub 项目，从公开项目文档或用户明确的平台上下文中推导 CLI/API；不要强行把 GitHub 命令套到其他托管平台上。

把 CI 当作结构化状态来轮询，而非流式文本：`gh run view <id> --json status,conclusion`（或该托管平台的等价物）。把 `gh run watch`、测试输出或构建输出通过 `tail`/`head` 管道传递，会吞掉真实的退出码，并可能把一次失败或仍在运行的运行报告成绿色。

## 验证

通过 tool_resource 获取测试运行脚本（`scripts/run-tests.sh`），然后从目标项目根运行它（脚本会从当前工作目录自动探测项目的测试命令），或运行项目已知的验证命令。粘贴完整输出。

如果脚本以非零退出，或打印 `(未检测到测试命令 - 请向用户询问验证命令)`：停下。不要声称完成。在继续之前先向用户询问验证命令。如果用户也无法提供，就在收尾签署中显式记录为 `verification: none -- no command available`，并把它标为一项结构性缺口，而非通过。

对于 bug 修复：在修复完成之前，必须存在一个在旧代码上会失败的回归测试。

在脏的或多 agent 的检出中，一次本地构建或测试通过并不能证明你的改动是可靠的：树中已有的无关 WIP 可能提供缺失的符号、掩盖一次断裂，或因与你无关的原因而失败。要在隔离环境中验证 —— `git worktree add --detach <known-good-commit>`，只 `git apply` 你拥有的那些文件的 diff，然后在那里构建/测试。干净的隔离通过才是真实信号；被污染的本地通过不是。

## 常见坑

| 发生了什么 | 规则 |
|---------------|------|
| 把公开回复发到了错误的 issue 或 PR 线程 | 先用 `gh issue view N` 或 `gh pr view N` 重读目标，确认标题、作者与当前状态后再动手 |
| PR 评论读起来像一份报告 | 1-2 句话，自然，像同事说话。不要结构化，不要像 AI。 |
| PR 评论用了项目符号 | 写成短段落，一段一个想法；先感谢贡献者 |
| 新文件名重复了语言、平台或后缀约定 | 创建或重命名文件之前，先检查目标目录既有的命名约定 |
| 未做提供商运行时或 env 检查就部署 | 遵循项目公开的部署文档，并把提供商配置与本机所需的 env 与运行时设置对照 |
| 因鉴权不匹配导致 push 失败 | 在新项目里首次 push 之前，检查 `git remote -v`、当前分支与鉴权身份 |

## 文档评审

对于文档、PDF、白皮书或散文评审，路由到 `/write`（Document Review Mode）。`/check` 只处理代码 diff 与发布产物。

## 收尾签署

用 `status` 行作为最终消息的开头，在表格或细节之前以纯文字给出：工作现在确切处在什么状态，带 hash、tag 或阻塞项。一个埋在验证表格之下的结论读起来像未完成，会让用户再问一遍「都提交了吗」；表格支撑结论，但它们不替代结论。

```
status:           [committed and pushed as <hash> / staged, not committed / released vX.Y.Z / blocked on <what>]
files changed:    N (+X -Y)
scope:            on target / drift: [what]
review depth:     quick / standard / deep
hard stops:       N found, N fixed, N deferred
sibling sweep:    N same-shape sites checked, N fixed / none found / not applicable
specialists:      [security, architecture] or none
new tests:        N
public actions:   replied #N, closed #N, reactions done / none pending
doc debt:         none / AGENTS.md needs X / rules need Y
verification:     [command] -> pass / fail
```

`public actions` 列出任务隐含的每一个对外步骤（issue 回复、关闭、发布表情），附上已完成或待办的状态；一个还得出用户来问的外部动作就是没做完。
