# Hunt：先定位根因，再动手修复

首行以内联方式加 🥷 前缀，不要单独成段。

针对症状打补丁，会在别处制造新的 bug。

## 结果契约

- 结果：在应用任何修复之前，先定位到根本原因。
- 完成条件：用一句话解释成因，所有观察到的症状都能套上它，且修复或交接针对一个可复现的检查得到验证。
- 证据：源码追踪、复现命令或 UI 路径、日志或状态、针对性的测试/构建输出，以及 UI 或原生缺陷的运行时证据。
- 输出：根本原因、修复或交接、验证结果，以及任何未清除的同类风险。
- 授权：「diagnose」「investigate」「why」「look into」「排查」「看看」或等价说法，都只是报告性质。只有当当前轮次明确要求修复、改动、实现或优化时，才应用修复；即便如此，仍必须先拿出根因证明。

**在你能用一句话说出根本原因之前，不要碰代码：**
> 「我认为根本原因是 [X]，因为 [证据]。」

点明具体的文件、函数、行或条件。「状态管理问题」无法被验证。「`src/hooks/user.ts:42` 处 `useUser` 里的陈旧缓存，因为依赖数组漏了 `userId`」才可验证。如果你说不这么具体，那就还没有假设。

## 诊断信号

假设的质量门槛：假设必须解释每一个可观察到的症状，而不只是最先被报告的那个；只覆盖一部分属于症状层面的猜测，不是根本原因。对依赖时序的问题（闪烁、间歇性失败、竞态），先可靠复现，再诊断。

自我合理化的迹象：「我就试试这个」= 没有假设，先把它写出来。「我很有把握」= 去跑那个能证明它的工具。「大概还是同一个问题」= 从头重读一遍执行路径。「在我机器上是好的」= 在排除之前先列出环境差异。「再重启一次」= 逐字读最后一条报错；没有新证据时，重启绝不超过两次。

## 持久上下文预检

当持久上下文在讨论范围内时，用 tool_resource 加载 `references/durable-context.md`，了解其适用范围，以及任何内容成为持久规则前所必须经过的脱敏关卡。

对 `/hunt` 而言：持久上下文只是假设的燃料，当前的代码、日志与复现证据优先于记忆。它绝不替代一句全新的根因陈述或一份可复现的症状清单。

## 硬性规则

- **修复后症状相同即硬性停止；「让我就试试这个」同样如此。** 两者都意味着假设还没做完。在再次碰代码之前，从头重读执行路径。
- **三个假设都失败后，停下。** 用下方的交接格式，列出已检查了什么、排除了什么、还有哪些未知。询问接下来怎么做。
- **断言之前先验证。** 绝不凭记忆陈述版本号、函数名或文件位置。先跑 `sw_vers` / `node --version` / grep。没有结果 = 重新检查路径。
- **外部工具失败：先诊断，再切换。** 当某个 MCP 工具或 API 失败时，先弄清原因（服务器在跑吗？API key 有效吗？配置对吗？），再去试替代方案。
- **系统/工具链症状需要更底层的基线。** 在归咎于可见的 app、生成的文件或顶层功能之前，先测量原始的更底层：OS 采集 vs 后处理、运行时服务 vs UI、编译器/工具链 vs 测试断言、网络/API vs 客户端处理。对基线已证伪的假设要予以淘汰，而不是围着它打转。
- **留意闪烁其词。** 当有人说「那部分不重要」时，把它当成一个信号。某人回避检视的地方，往往就是问题所在。
- **视觉/渲染 bug：先做静态分析。** 在加 console.log 或可视化调试浮层之前，先在 DevTools 里追踪绘制层、层叠上下文与层级顺序。日志无法捕捉合成器的行为。只有在静态分析失败之后，才加入插桩。
- **行为 / 生命周期 / 异步 bug：先插桩，而不是失败之后才插。** 窗口生命周期、事件投递、导航、焦点、定时器、状态机与异步顺序类的 bug，几乎不会仅靠静态阅读就能解决。不要等到修复失败才加日志。当你的假设一开始就涉及「这个回调在某者之前/之后触发」「当 Y 运行时这个状态应当是 X」「这个对象在这里应当仍然存活」时，**立刻把日志加上，作为形成假设的一部分**，在写任何修复之前。没有运行时证据的假设只是猜测；连续两次猜测就是硬性停止的信号。要和视觉渲染类 bug（合成器行为要靠 DevTools 而非日志）以及纯逻辑 bug（公式写错、差一错误）区分开——后者静态分析就足够。
- **魔数调到第三轮以上：停下，统一。** 当某个间距 / 尺寸 / 阈值被调整了三次仍然看着不对时，问题就是结构性的，而不是数值性的。把 N 个各自独立的值替换成一个具名 token（`Spacing.s4`、`--gap-content` 等），并核实那种不对称其实掩盖了一个缺失的约束。调参之后仍然存在的不对称是结构性的；继续调参不会收敛。
- **性能抱怨需要数字。** 对 Native App Freeze Mode 之外的「慢」「卡」或内存增长报告，先测量基线（墙钟时间、profile 采样、内存占用），修复，然后重新测量并报告前后数字。「感觉变快了」不是证据。
- **修根因，不修症状。** 如果修复触及超过 5 个文件，停下来与用户确认范围。

## 修复范围纪律

如果这个 bug 确实需要先做重构（例如不改动某个共享接口就无法触及根因），停下来，明确点出这次重构，并询问。不要悄悄把它捆绑进来。一个膨胀成重构的 bug 修复，是另一个 PR。

## 二分模式

启用条件：「以前是好的」「之前是好的」「used to work」「上一次提交还是对的」「broke after update」，或用户记得某个特定的好提交或版本。

- 先保护用户的工作区：`git status --short --branch -uall`。只要有已修改、已暂存或未跟踪的文件，就不在当前检出里做二分：改为在一个临时的 detached worktree 里跑，结束后删除该 worktree。如果无法使用临时 worktree，就停下，请求用户明确批准清理/stash。
- 如果最后已知良好版本只隔了少数几个发布，先 `git diff <last-good>..HEAD -- <suspect path>` 读一遍增量。回归通常在那里就能看见，成本只是二分的一小部分；只有 diff 太大或罪魁不明显时，才退回到二分。
- 只在事先定义好一条非交互式的 pass/fail 命令时才二分，并把记账留在 git 里（`git bisect good/bad`），包括直接测试某个可疑提交时。当它点出罪魁后，只把那份 diff 读到具体行，然后在删除临时 worktree 之前先跑 `git bisect reset`。

## 反复回归 / 截图参考模式

当用户说同一个问题在修复之后仍然不对、提供了一份「good」截图/版本/文件，或把某个视觉结果描述为「以前是正确的」时启用。

把参考当作证据，而非装饰：用用户的原话列出每一个被报告和可见的症状（「still slow」「尖刺」「先显示上一个内容」）；确认参照基准（最后已知良好的提交、旧构建、fixture、截图、被描述出的预期状态）；在编辑之前先定义 pass/fail 检查；然后点明当前与参照之间的确切差异。当证据指向损坏的渲染、竞态、字体管线或状态路径时，不要把视觉缺陷一概说成「样式打磨」。如果同一个症状在一次尝试修复后仍然存在，停下来，依据证据重建假设；不要把补丁叠在一个已被证伪的解释上。

如果问题纯粹是主观的 UI 审美，转 `/ui`。如果是渲染、状态、时序、构建产物、字体生成，或相对某个已知良好版本的回归，就留在 `/hunt`。

## 影响面扫荡模式

在修复一个根因模式之后、宣布 bug 完成之前启用；也在用户说「举一反三」「举一反三深入看看」或「其他地方有没有同样问题」时启用。同样的形状常常藏在另外 N 个地方；一次忽略影响面的局部修复，会在代码树里留下 N - 1 个 bug。

提取该模式的签名（产生这个 bug 的那个具体函数、正则、API 调用、CSS 选择器、加锁动作、被跳过的校验或输入边界），并用 `grep -rn` 在整个仓库里搜它，排除生成目录、构建产物与 vendored 依赖；对于「一类 bug」的模式（「任何漏了锁的 handler」），要搜周围的形状，而不只是字面文本。对每一处匹配，书面回答：同样的 bug / 可以不动（为什么）/ 不确定（问用户）。不要悄悄跳过任何一处匹配，并且在影响面报告进入 Output 区块之前，不要宣称「已修复」。扫荡带出的无关 bug 只登记，不在这次 PR 里修，除非用户同意。

## 确认或丢弃

跑那个「若假设为假就会失败」的探针，然后读它。如果证据与假设矛盾，就彻底丢弃它，并依据探针刚展示的东西重新定位。不要把修复叠在一个已被证伪的假设上，也不要因为代码「看起来像」成因就保留某个假设。

## 运行时证据阶梯

在宣称某个 bug 已修复之前，用这套阶梯：

1. 源码追踪：点明那个能产生该症状的确切函数、状态转换、文件、行或条件。
2. 确定性复现：跑或写那个能产生它的最小命令、fixture、UI 路径或场景。
3. 日志/状态/缓存：检视那个能证明路径被走到的运行时状态，包括队列、DB 行、缓存、临时文件、生成产物或外部工具日志。
4. 构建/测试：跑那条能锻炼到该修复的窄测试或构建。
5. 真实运行时检查：对 UI、原生 app、浏览器、渲染或视觉 bug，打开 app/页面/产物，用截图或具体清单核实可见结果。

对 UI、原生 app、视觉、渲染或生成产物类的 bug，只编译是不够的。如果在当前环境里无法做运行时检查，说明为什么，并交接要核实的确切界面、命令或产物。

当报告者的环境就是缺失的那一级、且本地无法复现时，下一个产物是一段他们可以粘贴并运行的只读探针，而不是又一个假设。让它打印出环境、有争议的测量值，以及假设所依赖的一切的状态，且不要包含任何可能携带机密或私有路径的内容。不要假设你自己的任何布局：他们的安装方式、目录约定、locale、shell 与版本都不同，所以要去发现，而不是硬编码。把它作为一段可直接复制的纯文本交付，附一条要运行的命令和一段要贴回来的区块。两轮「你能不能查一下……」而不给探针，正是这套做法要取代的形态。

对于反复出现的一类失败，在加第二个修复之前，先用 tool_resource 加载 `references/failure-patterns.md`。

## 原生 App 卡死模式

当桌面或移动原生 app 报告转菊花、无响应、切换标签页卡死、首次打开卡顿、空闲唤醒停摆、浮层锁死，或有截图显示 app 卡死时启用。

在改动代码之前要采集的证据：

1. 确切的用户路径与版本：首次启动 vs 热启动、标签页或窗口切换、空闲时长、权限、显示器数量，以及任何能让卡死消失的设置。
2. 卡死期间的运行时抓取：`sample <process>`、近期的 app 日志、CPU 与内存占用、线程数，以及主线程是被阻塞、空转还是正在分配。
3. 首帧表面：视图 body 的工作、第一个 `.task`、同步的图标或元数据查找、文件系统扫描、URL 父级遍历、通知回调，以及 app/窗口唤醒处理器。
4. 修复之后的影响面搜索：把同样的 API 形状在整个仓库里搜一遍，尤其是路径父级遍历、同步图标加载、渲染路径里的元数据读取，以及运行在主线程上的回调。

常见的原生卡死陷阱：

- 启动、退出、权限、音频、显示器或工作区通知在主线程上做路径遍历、图标查找、文件系统扫描或进程枚举。
- 首次绘制时，在显示出可交互的外壳之前就先把完整的 app 列表、目录树、媒体缩略图集或系统状态表一次性灌满。
- 输入锁或全屏浮层没有为 Escape、app 失活、权限被拒、进程终止与窗口关闭提供一条有保障的拆除路径。
- 定时器或采样工作能在窗口隐藏、长时间空闲、睡眠/唤醒或 app 重新激活之后仍然存活。

对这个模式来说，只编译和只读源码的检查都不够。结果必须包含运行时抓取、出根因的那一帧或状态转换、针对性的回归护栏，以及任何已修复或明确判定为安全的同类匹配。

## 定向日志

每一条日志都是一个是/否问题：「如果它在 Y 之前打印 X，假设 A 就成立；否则 A 就死了。」无法判定某个假设成立与否的日志都是噪音。收尾之前删除临时日志；把常驻诊断放在项目的 debug 开关之后。如果加一条日志就改变了行为，那本身就是时序、生命周期或并发问题的证据。完整手册：用 tool_resource 加载 `references/logging-techniques.md`。

## 易错点

| 发生了什么 | 规则 |
|---------------|------|
| 改的是 client 面板而不是本地面板 | 在碰任何文件之前，先反向追踪执行路径 |
| MCP 没加载，却切换工具而不是诊断 | 在切换方法之前，先检查服务器状态、API key、配置 |
| 在测量原始系统/工具链层之前就归咎于可见的 app | 先测量更底层，然后明确淘汰已排除的假设 |
| Orchestrator 显示 RUNNING，但 TTS 供应商配错了 | 在多阶段流水线中，单独测试每一个阶段 |
| 把竞态条件诊断成了陈旧状态 bug | 对时序敏感的问题，先检查事件时间戳与顺序，再看状态 |
| 到处加日志，仍然解释不了这个 bug | 把每条日志改写成一个是/否问题。删掉无法判定假设成立与否的日志 |
| 本地能复现，CI 里却失败 | 先对齐环境（运行时版本、环境变量、时区），再去追代码 |
| 堆栈跟踪指向某个库的很深处 | 往回走 3 帧到你自己代码里；bug 几乎总在那里，而不在依赖里 |
| 从 app 里启动正常，经文件关联 / 拖放 / 深链 / 外部代理打开就坏 | 用用户描述的那个确切入口来复现。app 内部初始化与「带文件冷启动」的初始化不同；文档到达时状态可能还没就绪。 |
| 构建通过，但 UI 看起来仍然不对 | 沿着运行时证据阶梯往上走，去核实真正渲染出来的表面或产物。 |
| 修复只对上报告者的环境，对其他人毫无改变，或让默认行为回归 | 一份缺陷报告是证据，不是完整范围。说明该修复改变的是所有用户的默认体验，还是仅报告者的配置，并优先修默认路径。 |
| 切换主题 / 模式 / locale 之后就坏，重启后又好了 | 在切换路径上没有重新应用状态。先追踪该切换的重算或失效路径；在状态路径已经坏掉时，不要逐像素地调样式。 |
| 改了算法，输出却仍然不对 | 读取方可能拿到的是旧代码写入的持久化输出（扫描结果、分析缓存、带 TTL 的快照）。改动「先生成再持久化」的数据时，必须在同一次改动里让旧缓存失效或升版本；在重新诊断之前，先确认运行时没有读到陈旧数据。 |
| 报告者能复现，本地机器却正常，agent 却盲改 | 先给出一条可复制粘贴的诊断命令（单条命令、静默采集、一个输出文件、一句隐私说明），依据返回的证据来诊断，然后再修。 |

## 渲染 Bug 模式

启用条件：「PDF looks wrong」「page break issue」「font not rendering」、PDF 输出损坏，或打印版式不对。

用 tool_resource 加载 `references/rendering-debug.md`，获取完整的诊断清单（WeasyPrint 的怪癖、字体加载、页面溢出、浏览器打印 CSS）。先做静态分析，必要时再复现。

## IME / Unicode 问题

对于输入法、字符渲染或文本编码类的 bug（IME 状态、光标漂移、emoji 拆分、composition 事件），在形成假设之前，先用 tool_resource 查看 `references/ime-unicode.md`。

## 输出

### 成功格式

用一句平实的话开头收尾，说明结果以及改动是否已提交；下面的区块是支撑这句话的，不能取而代之。

```
Root cause:        [what was wrong, file:line]
Fix:               [what changed, file:line]
Sibling sweep:     [N same-shape sites checked, N fixed / none found / not run, why]
Confirmed:         [evidence or test that proves the fix]
Tests:             [pass/fail count, regression test location]
Regression guard:  [test file:line] or [none, reason]
```

状态：**resolved**、**resolved with caveats**（说明有哪些），或 **blocked**（说明还有什么未知）。

**回归护栏规则**：对任何复发过、或此前被「修复」过的 bug，满足以下条件才算修好：

1. 存在一个在未修复代码上失败、在已修复代码上通过的回归测试。
2. 该测试位于项目的测试套件里，而非临时文件。
3. 提交信息说明 bug 为何复发，以及这次修复为何能防止它。
4. Red-green 是**跑出来的**，不是假设的：回退修复（或 stash 掉），看新测试失败，恢复修复，看它通过。一个从来只被观察到通过的回归测试，什么也钉不住。在输出里写明那次 red 运行。有两种形态会让它静默失效，且两种都已上线过：一种框架或语法里，测试中途失败的断言不会让测试失败，于是只有最后一个断言在把关（在 shell 测试套件里，这可能仅取决于括号形式，一个关键字被吞掉、另一个被捕获，所以要通过跑一个两行的最小复现来确认到底是哪种，而不是靠推理）；以及一个断言「某错误字符串不存在」，它会永远通过，因为那个字符串在任何代码版本下都从未被输出过。任何否定式断言（「输出中不得包含 X」）还需要在同一个测试里配一个正向用例，证明这个断言有失败的可能。
