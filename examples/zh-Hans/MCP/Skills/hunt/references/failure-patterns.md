# 失败模式参考

当某个 bug 反复出现、第一次修复没能撑住，或症状闻起来像是运行时状态而非局部代码语法时，使用本参考。

## 陈旧的验证器或工具缓存

信号：验证器输出指向已删除的临时 worktree、旧的生成文件，或当前仓库之外的路径；干净检出后重跑，文件路径变了，但当前代码没变。

检查：
- 确认被报告的路径确实存在。
- 在证明确实陈旧之后，才清理工具缓存。
- 从当前仓库根目录重跑同一个验证器。

## Worker 队列或 DB 边界

信号：UI 显示任务在跑，但没有 worker 在处理它；日志显示调度器有活动，却没有排队行；重试修好了单个条目，却没修好整条流水线。

检查：
- 追踪 request -> enqueue -> worker 取出 -> 持久化 -> UI 刷新。
- 直接检视队列行或 job 状态。
- 在入队边界周围加一个回归测试，而不只是在 worker 主体上。

## 生成物重建边界

信号：源码改了，但生成产物、app bundle、CLI 制品、归档、校验和或发布包仍包含旧行为。

检查：
- 找出 source-to-artifact 的规则。
- 核实构建系统监听了源码路径。
- 检视生成产物的内容，而不只是源码 diff。

## 守卫生命周期竞态

信号：权限、鉴权或状态守卫在本地看起来正确，但一个延迟回调、app 重启或替代入口绕过了它。

检查：
- 追踪守卫的创建、保留、失效，以及每一个替代入口。
- 在适用时核实冷启动、热启动、深链/文件打开与重试路径。
- 当守卫必须在重启后仍然存活时，优先使用显式的持久状态，而不是瞬时标志。

## 原子临时文件名

信号：并发运行相互碰撞、清理删错了文件，或观察到写了一半的输出。

检查：
- 使用唯一的临时目录或原子 rename。
- 让清理只作用于本次运行创建的文件。
- 在工具支持时，测试两次并发或背靠背运行。

## 路径、Cwd 或符号链接逃逸

信号：一个本应作用于某个根的操作碰到了兄弟目录、出乎意料地跟随了符号链接，或在不同工作目录下行为不同。

检查：
- 在写入或删除之前，解析并比较规范化后的根。
- 在符号链接解析之后，拒绝允许根之外的路径。
- 从非默认 cwd、以及任何会提供路径的 UI 入口来复现。

## CLI 作用范围漂移

信号：预览、dry-run、大小、数量或报告输出是按一个谓词算出来的，但执行时改动的却是更大或不同的一组。

检查：
- 把展示、dry-run 与变更所用的谓词追溯到同一个事实来源。
- 在回归测试中，把计划处理的路径或记录与执行器的输入做对比。
- 断言部分失败时报告出确切的跳过与完成条目。

## CLI 包装器或 PATH 漂移

信号：从源码树调用正常，但已安装的命令、包包装器、PATH shim、补全脚本或包管理器安装路径跑的是旧代码或另一个二进制。

检查：
- 检视构建好的包内容、shebang、可执行位与包装器目标。
- 通过临时前缀或包管理器安装路径来复现，而不只是从源码。
- 检查 PATH 顺序，在不应被包装器拦截的地方使用系统工具的绝对路径。

## 交互式 Stdin 或 TTY 挂起

信号：CI 卡住、转圈永不结束、子进程从脚本体读走了数据，或非交互模式下弹出了鉴权提示。

检查：
- 分别在重定向 stdin、以及把 TTY/非 TTY 路径分开的情况下复现。
- 在真实的提示与系统变更周围加上 test-mode 或 no-auth 守卫。
- 当超时包装器 exec 真实二进制时，通过 PATH 把外部提示工具打桩。

## 子进程管道背压

信号：长时间运行的子进程只在输出很大时才挂起，小 fixture 能通过，或父进程在读取 stdout/stderr 之前就等退出。子进程可能被写满的管道缓冲区阻塞，而父进程被 `wait` 阻塞。

检查：
- 在进程运行时持续排空 stdout 与 stderr，或在不需要输出时显式继承/重定向流。
- 用大于典型管道缓冲区的输出做测试，而不只是微小的 fixture。
- 保留 stderr 尾部或结构化错误输出以供诊断，同时不要把整条流都攥在内存里。

## 信号或部分失败的映射

信号：cancel、超时、SIGINT 或 SIGTERM 被报告成成功或普通的业务失败；临时文件、锁或操作日志让重试看起来已经完成。

检查：
- 把被中断的执行与成功、以及预期的校验失败分开归类。
- 断言中断之后的临时清理、锁释放与操作日志状态。
- 测试部分写入之后的重试与幂等性。

## CLI 流契约回归

信号：在人类可读日志、进度输出、JSON 形状、stdout/stderr 路由或退出码行为变化之后，自动化就崩了。

检查：
- 在 CLI 测试中，分别断言退出码、stdout 与 stderr。
- 在机器可读模式下，让人类可读诊断信息不要写到 stdout。
- 对 JSON/schema 输出做快照或解析，并纳入非交互式覆盖。

## 快照重建丢失携带字段

信号：实时数据在数据源和传输线上都出现了，但下游视图看到的却是空的；该字段有一个默认值（`var x: [T] = []`、`var y: Int? = nil`），使得 memberwise init 不带它也能编译通过；症状只出现在重建快照的那条路径上（图标解析、装饰、脱敏），而不出现在全新拉取时。

检查：
- 追踪构造该快照类型的每一条代码路径是否都传入了这个字段。Swift 编译器不会对 memberwise init 里的默认值省略发出警告。
- 加一个单元测试：拉取快照、跑重建路径，并断言被携带的字段等于输入。
- 当只有一个字段在变时，优先用 `with(...)` 之类的可变辅助方法或 `inout` 变更，而不是全新的 memberwise init。

## 多采样命令的冷启动

信号：一个接受 `-l N` / `--samples N` / `--repeat N` 的 CLI 工具返回一段全零和一段真实数据；把全部采样聚合起来得到的是零；只有第二个采样带有真实测量值。

检查：
- 读该工具的 man 手册了解冷启动语义。`top -l 2`、`iostat -d 2`、`vm_stat 1 2` 等都是这个形状。
- 把输出切到最新的那个采样（对解析后的行取 `.suffix(perSampleSize)`，或找表头行第二次出现的位置）。
- 拿不准时把 `-l` 提到 3，确认采样 2 与 3 一致；采样 1 仍然是零。

## 依赖 locale 的子进程输出

信号：数字在作者机器上解析正常，但在部分用户那里返回零、被截断或错得离谱；百分比、大小或时长在某个地区正常、在另一个地区就坏；同一个解析器此前已经为另一个字段打过一次补丁。

检查：
- 给每一个其输出会被解析的子进程强制一个固定的 locale（`LC_ALL=C` 或平台等价物），而不是逐个解析器去修逗号小数点、数字分组或翻译后的字段标签。
- 在 spawn 的边界上修，而不是逐个调用点修。这个形状会以三到四份独立报告的形式到来（先是某个指标，然后又一个，然后是一份渲染出来的摘要），每一次点状修补都会掩盖还有多少个解析器仍然暴露在外。
- 把翻译后的输出当成格式变更，而不是字符串变更：字段顺序、单位与标签名都可能变。

## 单探针存在性检查

信号：一个「它是否已安装 / 正在运行 / 已注册 / 处于活动」的判定对一部分用户是错的，而这个错误判定又会驱动一个破坏性或用户可见的动作（被标记为孤立、被提示删除、某项功能被静默禁用）。这部分用户共享某种安装方式、打包约定，或探针不知道的某个 OS 特性。

检查：
- 列出该对象可能存在的每一种正当方式，然后确认探针都能看到。一次索引查询、一次 PATH 查找、一个进程名或一个接口名前缀都是片面的视图：系统索引可能被禁用或跳过某种打包约定，嵌套或内嵌的组件不会像顶层组件那样被注册，而 OS 自有的接口会借用第三方功能也在用的命名。
- 区分「探针超时」与「对象不存在」。索引慢是未知，不是不存在的证明；一条超时的快路径必须落到直接检查上，绝不落到否定判定上。
- 对失败做非对称加权：当判定会授权删除时，一个错误的「不存在」会毁掉数据，而一个错误的「存在」只是留下点东西。在走破坏性分支之前，要求来自第二个来源的佐证。

## 聚合键变体

信号：某个计数、日志汇聚、事件统计或按类别的拆分少了一些条目；缺失的条目共享某个特征（一条由系统派生的路径、一个本地化字符串、一个带前缀的命令名）；基础形态的键能匹配上，但某个派生变体（`<base>-system`、一个后缀、一个前缀）被静默丢弃。

检查：
- 在新增一个类别之前，grep 每一个会产生这类键的写入点，枚举出真正的变体，而不只是基础形态。
- 用 `hasPrefix` / 正则 / 一个显式的变体清单来匹配，而不是对基础键做精确相等。
- 为每一个已知变体加一行 fixture，这样将来某个能逃过匹配器的键形状会让测试失败，而不是让聚合结果出错。

## 整缓冲区解码崩塌

信号：一个在你机器上正常的解析器在别人机器上什么都读不出；受影响的用户有带重音的设备名、非 ASCII 文件名或异常的进程参数；失败是整体性的（所有行都没了），而不是部分性的（某一行乱码）。这与管道背压不同：字节到了，是解码把它们扔掉了。

检查：
- 找出每一个对子进程、设备或文件系统产出的字节所做的严格解码（`String(data:encoding:)`、`from_utf8`、不带 `errors=` 的 `decode('utf-8')`）。一个非法字节就会让整个缓冲区变成 nil，而把 nil 合并成空的调用方会把它变成「这条命令什么都没产出」。
- 只要字节是一份待解析的报告，就宽松地解码；只在字节是被校验的签名或校验和时才保留严格解码，并在那里 fail closed。两种立场属于同一个代码库里不同的调用点。
- 检查空结果在下游意味着什么。一个把空的进程列表读成「没有东西在运行」的安全守卫是 fail open 的，而这在一条破坏性路径上是危险的方向。
- 真正的失败由退出状态与超时来报告，而不是由解码是否成功。把调用方指向那些。

## 被拒绝的读返回一个看似合理的值

信号：某个指标对一部分对象正确、对另一部分错误，且这种分化沿着所有权走：你自己的进程/文件是正确的，root 所有或他人用户的则读出零、陈旧或不存在。因为 API 应答了，所以没有记录任何错误。

检查：
- 去测量边界，而不是读文档：把该调用跑在自有与非自有对象上，数一数有多少成功。「33 个自有的里 33 个成功，5 个 root 的里 0 个」就是证据；猜测不是。
- 检查被拒读的兜底是否与主来源承载相同的含义。同一列里出现两种不同含义就是 bug，即使每个值单独看都说得通。
- 优先选一个对每个对象都一致作答的来源（一个不分所有者、报告所有进程的工具），而不是一个对某些对象静默降级的精确来源。

## 以它所恢复的产物为门控的恢复

信号：一条修复、重装或自愈路径无论跑多少次都报告同一个死胡同；损坏状态在重装之后依然存在；这条修复「一直都在」，却没有任何证据表明它曾经成功过。

检查：
- 读一读这条修复路径自己的前置条件，问它在那个它本就是为了修复的损坏状态里是否成立。一条以那个正缺失的文件为门控的恢复，永远不可能触发。
- 核实修复命令里每一个绝对工具路径在该平台上确实存在。一个路径写错就会以非零退出，`&&` 链会静默中断，这条修复就会在每一台机器上永远空转。加一个测试，走一遍命令里的每个路径并断言它可执行。
- 不要让测试断言这条修复命令的源码形状；那等于把损坏的形态钉成正确的。改为断言可观察的最终状态（服务已注册、文件已存在、探针有应答）。
- 让修复自己拥有结果，而不是假设结果：写出产物，再通过查询系统来证明它，并把查询的原始输出记录下来，而不是丢弃。

## 按快路径调校的看门狗

信号：某个操作实际上健康，却被报告成失败、停滞或「没有进展」；报告来自处在慢网络、冷缓存、网络卷或大负载下的用户；重试时每次都在相同的耗时处失败。

检查：
- 对每一个超时常量，点名最慢的*健康*情形（在慢网络上下载几百 MB、一天之中的首次索引重建、某工具在清理之后重建缓存），并确认该常量留有余量地越过它。这与魔数等待的耦合相反：那种情况下定时器太松、不构成真实信号，而这里它太紧、容不下一个健康的慢情形。
- 把「N 秒没有输出」换成真正的存活探针（一个不断增长的临时文件、一个字节计数器、一次心跳），并把超时留作真正的停摆守卫。
- 对每个看门狗，枚举它守护区域内每一条退出路径，包括抛出的错误和岔入替代路径的 fork。一个能扛过 fork 的看门狗，会在取代它的那条路径中途触发。
- 检查是否已有第二个上界覆盖了真正挂死的运行。若是，这个额外的定时器就只能提前触发。

## 显示字符串比较

信号：一次基于面向用户文本的比较产出一个永远无法收敛的判定：一个永远「有更新可用」却又什么都不装的提示、一个总是报告已变更的 diff、一个永不触发的匹配。两侧对同一个底层值采用了不同的格式。

检查：
- 问一问被比较值的*格式*究竟属于契约的一部分，还是生产者随意重排的东西。版本显示字符串、从 URL 尾部派生的文件名，以及本地化标签，都是自由格式。
- 找出平台为排序或相等性所设想的、面向机器的身份（一个 build 号、一个内容哈希、一个 id），比较那个，只在两侧任一都缺少该身份时才回退到显示形态。
- 当兜底必须保留时，在两侧字符串携带的是同一串 token 但排列不同的地方，抑制该判定；任何真正更新或已变更的值都不可能满足这一点。
- 修掉每一处重复该比较的通道，而不只是产生报告的那一处。这个形状几乎总是被复制了多份。
